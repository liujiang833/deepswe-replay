# 基于 `per_tool_merged.xlsx` 的代表性负载选取说明书（草案）

## 1. 目的

从 `per_tool_merged.xlsx` 中筛选排序靠前的 50% 聚类，并从每个入选聚类中选取一个代表性负载，用于后续性能测试、体系结构分析或负载集构建。

本方案优先保留总执行时间较长、对整体运行贡献较大的聚类，同时保证每个入选聚类只对应一个可追溯、可复现的负载。

## 2. 适用范围与默认口径

本文采用以下默认口径：

1. “一个 clustering”指 Excel 中的一条有效聚类记录，而不是一条原始命令。
2. “前 50%”指按 `wall_s` 从大到小排序后，取聚类数量的前 50%，不是取累计执行时间达到 50% 的聚类。
3. 若有效聚类数为 `N`，入选数量为 `ceil(N × 50%)`；奇数时向上取整。
4. 排序在全部有效聚类上统一进行。若项目要求每一种工具都必须被覆盖，应改用“按 `program` 分组后，各组分别取前 50%”的分层方案，不能直接使用全局前 50%。
5. 每个聚类只选一个代表性 step。一个 step 可能包含多条命令，这些命令共同构成该代表性负载，不应只执行 `rep_cmd` 显示的一条命令。

> 注意：如果“前 50%”实际是指累计 `wall_s`、累计 `cycles` 达到 50%，应另行计算累计占比，不能使用本说明中的按数量截断方法。

## 3. 输入数据

### 3.1 必需文件

- `per_tool_merged.xlsx`：提供聚类编号、工具类型、规模、性能特征和代表样本索引。
- 原始 step 明细表，通常为 `steps.xlsx`：用于根据 `rep_trial` 和 `rep_step` 找回完整命令序列及执行上下文。

### 3.2 主要字段

| 字段 | 用途 |
|---|---|
| `cluster_id` | 聚类唯一标识，也是选取结果的主键 |
| `program` | 工具或程序类型，用于分类、分层抽样和覆盖率检查 |
| `n_steps` | 聚类包含的 step 数量 |
| `wall_s` | 聚类内 step 的总执行时间，默认排序依据 |
| `cycles` | 聚类消耗的总 CPU cycles，用于辅助判断资源贡献 |
| `pct_cycles` | cycles 占比；使用前需确认其分母口径 |
| `Retiring%`、`BadSpec%`、`FrontendBound%`、`BackendBound%` | 聚类的 Top-Down 特征中心 |
| `max_spread` | 聚类内部四维特征的最大跨度，用于判断聚类紧致程度 |
| `rep_trial` | 代表 step 所属 trial |
| `rep_step` | 代表 step 编号 |
| `rep_cmd` | 代表 step 首条非空命令的截断预览，只用于人工识别 |

## 4. 选取原则

### 4.1 聚类筛选原则

1. 只保留 `cluster_id`、`program`、`wall_s`、`rep_trial`、`rep_step` 均有效的记录。
2. 默认按 `wall_s` 降序排列；`wall_s` 相同时依次按 `cycles` 降序、`cluster_id` 升序排列，保证结果可重复。
3. 从排序结果中取前 `ceil(N/2)` 条。
4. 不直接依赖 Excel 当前行号或底色。即使源文件通常已经排序，也应重新按字段排序后再截断。
5. 不将 `pct_cycles` 直接作为全表排序依据，除非已经确认所有行的占比采用同一个分母。

### 4.2 聚类内代表负载原则

原始聚类的四维向量为：

```text
(Retiring, BadSpec, FrontendBound, BackendBound)
```

聚类中心为各成员按 `cycles` 加权得到的质心。代表 step 原则上取与该质心 L∞ 距离最小的成员，即：

```text
distance(step, centroid)
  = max(|Ret-Ret_c|, |Bad-Bad_c|, |FE-FE_c|, |BE-BE_c|)
```

因此，若 Excel 中已有可信的 `rep_trial` 和 `rep_step`，直接采用二者指向的 step；不要另行选择耗时最大或 cycles 最大的单条命令代替。

完整负载必须从 step 明细表中回查：

```text
trial == rep_trial AND step == rep_step
```

回查所得的完整 `commands`、执行顺序、工作目录、环境和超时策略共同定义该负载。`rep_cmd` 可能被截断，不能单独作为重放脚本。

## 5. 标准操作流程

### 步骤 1：冻结输入版本

记录 Excel 文件名、生成时间、文件哈希、聚类阈值和数据批次。后续若源文件更新，应重新执行选取，不要沿用旧结果中的行号。

### 步骤 2：清洗有效聚类

删除空行、汇总行、重复 `cluster_id` 以及缺失代表样本定位字段的行。数值列应转换为数值类型；无法转换的记录进入异常清单，不参与自动筛选。

建议同时检查：

- `n_steps >= 1`；
- `wall_s >= 0`、`cycles >= 0`；
- 四个 Top-Down 百分比均在合理范围内，且合计接近 100%；
- `max_spread` 未超过本批次约定的聚类阈值；
- `rep_trial + rep_step` 在 step 明细中唯一命中一条记录。

### 步骤 3：确定前 50% 聚类

设清洗后的有效聚类数为 `N`，计算：

```text
K = ceil(N / 2)
```

按以下顺序排序并选择前 `K` 条：

```text
wall_s DESC, cycles DESC, cluster_id ASC
```

例如，有效聚类数为 21，则选取前 11 个；有效聚类数为 20，则选取前 10 个。

### 步骤 4：提取代表性负载

对每个入选聚类：

1. 读取该行的 `rep_trial` 和 `rep_step`；
2. 在 step 明细中定位唯一记录；
3. 提取完整 `commands` 及其执行上下文；
4. 记录该负载对应的 `cluster_id`、`program` 和四维特征；
5. 给负载分配稳定 ID，建议格式为 `WL-<序号>-<program>-<cluster_id>`。

### 步骤 5：去重与可执行性检查

若两个聚类最终指向完全相同的 `trial + step`，不得静默保留两个副本。应先检查是否为合并表或映射过程造成的重复：

- 若两个聚类语义确实不同，保留两条选取记录，但只保存一份负载实体，并记录一对多映射；
- 若是数据错误，修正源映射后重新选取；
- 不建议擅自用同簇第二近样本替换，除非重新计算其到聚类中心的距离并留下替换原因。

随后进行一次最小化试运行，确认命令可解析、依赖可用、路径存在、超时设置有效，并记录退出码。原始失败本身可能属于真实负载特征，因此不能仅因退出码非零就删除；只有环境损坏、数据缺失或无法启动时才判为不可执行。

### 步骤 6：验证代表性

条件允许时，对代表负载至少重复运行 3 次，并比较其 Top-Down 四维向量与所属聚类中心：

```text
replay_distance = max(|replay[d] - cluster_center[d]|)
```

建议验收条件：

- `replay_distance` 不超过原聚类阈值；
- 三次运行的关键指标没有明显漂移；
- 命令序列、退出状态和主要输出结构与原始记录一致；
- 代表负载可在目标环境中独立重放。

若验证失败，优先排查机器状态、依赖版本、缓存、后台进程和采集配置。确认环境无误后，才从同一聚类中改选距离质心第二近的可执行 step，并记录替换理由。

## 6. 合并聚类的特别处理

`per_tool_merged.xlsx` 中的 `cluster_id` 可能形如 `program#C1_C2`，表示一行合并了多个相邻的原始聚类。此时必须先确认选取目标：

- 若把 Excel 每一行视为最终聚类单元，可直接使用该行的 `rep_trial + rep_step`；
- 若要求“每个原始 clustering 选一个负载”，应拆回 `C1`、`C2`，从未合并的 per-tool 聚类表分别选择，不能让合并行只产生一个负载。

当前生成逻辑下，合并行的代表样本可能来自合并前 `wall_s` 最大的子聚类，而不是对合并后全部成员重新计算得到的质心代表。因此，若合并行将被当作一个新的统计聚类，建议重新基于全部成员计算 cycles 加权质心和最近样本。

## 7. 输出要求

最终建议输出一份 `selected_workloads.xlsx` 或 CSV，至少包含：

| 字段 | 说明 |
|---|---|
| `workload_id` | 负载唯一编号 |
| `rank` | 在有效聚类中的排序 |
| `cluster_id` | 来源聚类 |
| `program` | 工具类型 |
| `n_steps` | 来源聚类规模 |
| `wall_s`、`cycles` | 来源聚类资源贡献 |
| 四个 Top-Down 指标 | 来源聚类特征中心 |
| `max_spread` | 聚类紧致度 |
| `rep_trial`、`rep_step` | 代表 step 定位信息 |
| `commands` | 完整命令序列，不使用截断预览代替 |
| `selection_rule` | 例如 `top_50pct_by_count/wall_s` |
| `validation_status` | `pending`、`passed` 或 `replaced` |
| `replacement_reason` | 若发生替换，填写具体原因 |
| `source_hash` | 输入文件版本标识 |

同时输出未入选聚类清单和异常清单，使结果可复核、可重现。

## 8. 验收标准

负载集满足以下条件时可交付：

1. 入选聚类数严格等于 `ceil(N/2)`；
2. 每个入选聚类恰好映射到一个代表负载；
3. 所有代表负载都能追溯到唯一的 `rep_trial + rep_step`；
4. 完整命令来自 step 明细，而不是来自截断的 `rep_cmd`；
5. 排序、并列处理、异常排除和代表替换均有记录；
6. 合并聚类的解释口径已经明确，并在结果中注明；
7. 试运行和代表性验证结果完整保存。

## 9. 方法边界

本方法代表的是选定指标空间中的 CPU 微架构特征，不自动保证语言、业务场景、命令意图、I/O 行为、内存占用或长尾时延同样具有代表性。若最终负载集还需要这些维度的覆盖，应在“前 50%”筛选之后增加分层覆盖或多指标约束，而不能只依赖 Top-Down 聚类结果。
