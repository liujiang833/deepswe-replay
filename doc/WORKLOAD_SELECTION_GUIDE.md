# 基于 `per_tool_merged.xlsx` 的代表性负载选取说明书（草案）

## 1. 目的

从 `per_tool_merged.xlsx` 中筛选排序靠前的 50% 聚类，并从每个入选聚类中选取一个代表性负载，用于后续性能测试、体系结构分析或负载集构建。

本方案优先保留总执行时间较长、对整体运行贡献较大的聚类，同时保证每个入选聚类只对应一个可追溯、可复现的负载。

## 2. 适用范围与默认口径

本文采用以下默认口径：

1. “一个 clustering”指 Excel 中的一条有效聚类记录，而不是一条原始命令。
2. “前 50%”指按 `wall_s` 从大到小排序后，取聚类数量的前 50%，不是取累计执行时间达到 50% 的聚类。
3. 若有效聚类数为 `N`，入选数量为 `ceil(N × 50%)`；奇数时向上取整。
4. 排序在全部有效聚类上统一进行。若项目要求每一种工具都必须被覆盖，应改用“按 `program` 分组后，各组分别取前 50%”的分层方案，不能直接使用全局前 50%。
5. 每个聚类只选一个代表性 step。一个 step 可能包含多条命令，这些命令共同构成该代表性负载，不应只执行 `rep_cmd` 显示的一条命令。

> 注意：如果“前 50%”实际是指累计 `wall_s`、累计 `cycles` 达到 50%，应另行计算累计占比，不能使用本说明中的按数量截断方法。

## 3. 输入数据

### 3.1 必需文件

- `per_tool_merged.xlsx`：提供聚类编号、工具类型、规模、性能特征和代表样本索引。
- 原始 step 明细表，通常为 `steps.xlsx`：用于根据 `rep_trial` 和 `rep_step` 找回完整命令序列及执行上下文。

### 3.2 主要字段

| 字段 | 用途 |
|---|---|
| `cluster_id` | 聚类唯一标识，也是选取结果的主键 |
| `program` | 工具或程序类型，用于分类、分层抽样和覆盖率检查 |
| `n_steps` | 聚类包含的 step 数量 |
| `wall_s` | 聚类内 step 的总执行时间，默认排序依据 |
| `cycles` | 聚类消耗的总 CPU cycles，用于辅助判断资源贡献 |
| `pct_cycles` | cycles 占比；使用前需确认其分母口径 |
| `Retiring%`、`BadSpec%`、`FrontendBound%`、`BackendBound%` | 聚类的 Top-Down 特征中心 |
| `max_spread` | 聚类内部四维特征的最大跨度，用于判断聚类紧致程度 |
| `rep_trial` | 代表 step 所属 trial |
| `rep_step` | 代表 step 编号 |
| `rep_cmd` | 代表 step 首条非空命令的截断预览，只用于人工识别 |

## 4. 选取原则

### 4.1 聚类筛选原则

1. 只保留 `cluster_id`、`program`、`wall_s`、`rep_trial`、`rep_step` 均有效的记录。
2. 默认按 `wall_s` 降序排列；`wall_s` 相同时依次按 `cycles` 降序、`cluster_id` 升序排列，保证结果可重复。
3. 从排序结果中取前 `ceil(N/2)` 条。
4. 不直接依赖 Excel 当前行号或底色。即使源文件通常已经排序，也应重新按字段排序后再截断。
5. 不将 `pct_cycles` 直接作为全表排序依据，除非已经确认所有行的占比采用同一个分母。

### 4.2 聚类内代表负载原则

原始聚类的四维向量为：

```text
(Retiring, BadSpec, FrontendBound, BackendBound)
```

聚类中心为各成员按 `cycles` 加权得到的质心。代表 step 原则上取与该质心 L∞ 距离最小的成员，即：

```text
distance(step, centroid)
  = max(|Ret-Ret_c|, |Bad-Bad_c|, |FE-FE_c|, |BE-BE_c|)
```

因此，若 Excel 中已有可信的 `rep_trial` 和 `rep_step`，直接采用二者指向的 step；不要另行选择耗时最大或 cycles 最大的单条命令代替。

完整负载必须从 step 明细表中回查：

```text
trial == rep_trial AND step == rep_step
```

回查所得的完整 `commands`、执行顺序、工作目录、环境和超时策略共同定义该负载。`rep_cmd` 可能被截断，不能单独作为重放脚本。

## 5. 标准操作流程

### 步骤 1：冻结输入版本

记录 Excel 文件名、生成时间、文件哈希、聚类阈值和数据批次。后续若源文件更新，应重新执行选取，不要沿用旧结果中的行号。

### 步骤 2：清洗有效聚类

删除空行、汇总行、重复 `cluster_id` 以及缺失代表样本定位字段的行。数值列应转换为数值类型；无法转换的记录进入异常清单，不参与自动筛选。

建议同时检查：

- `n_steps >= 1`；
- `wall_s >= 0`、`cycles >= 0`；
- 四个 Top-Down 百分比均在合理范围内，且合计接近 100%；
- `max_spread` 未超过本批次约定的聚类阈值；
- `rep_trial + rep_step` 在 step 明细中唯一命中一条记录。

### 步骤 3：确定前 50% 聚类

设清洗后的有效聚类数为 `N`，计算：

```text
K = ceil(N / 2)
```

按以下顺序排序并选择前 `K` 条：

```text
wall_s DESC, cycles DESC, cluster_id ASC
```

例如，有效聚类数为 21，则选取前 11 个；有效聚类数为 20，则选取前 10 个。

### 步骤 4：提取代表性负载

对每个入选聚类：

1. 读取该行的 `rep_trial` 和 `rep_step`；
2. 在 step 明细中定位唯一记录；
3. 提取完整 `commands` 及其执行上下文；
4. 记录该负载对应的 `cluster_id`、`program` 和四维特征；
5. 给负载分配稳定 ID，建议格式为 `WL-<序号>-<program>-<cluster_id>`。

### 步骤 5：去重与可执行性检查

若两个聚类最终指向完全相同的 `trial + step`，不得静默保留两个副本。应先检查是否为合并表或映射过程造成的重复：

- 若两个聚类语义确实不同，保留两条选取记录，但只保存一份负载实体，并记录一对多映射；
- 若是数据错误，修正源映射后重新选取；
- 不建议擅自用同簇第二近样本替换，除非重新计算其到聚类中心的距离并留下替换原因。

随后进行一次最小化试运行，确认命令可解析、依赖可用、路径存在、超时设置有效，并记录退出码。原始失败本身可能属于真实负载特征，因此不能仅因退出码非零就删除；只有环境损坏、数据缺失或无法启动时才判为不可执行。

### 步骤 6：验证代表性

条件允许时，对代表负载至少重复运行 3 次，并比较其 Top-Down 四维向量与所属聚类中心：

```text
replay_distance = max(|replay[d] - cluster_center[d]|)
```

建议验收条件：

- `replay_distance` 不超过原聚类阈值；
- 三次运行的关键指标没有明显漂移；
- 命令序列、退出状态和主要输出结构与原始记录一致；
- 代表负载可在目标环境中独立重放。

若验证失败，优先排查机器状态、依赖版本、缓存、后台进程和采集配置。确认环境无误后，才从同一聚类中改选距离质心第二近的可执行 step，并记录替换理由。

## 6. 合并聚类的特别处理

`per_tool_merged.xlsx` 中的 `cluster_id` 可能形如 `program#C1_C2`，表示一行合并了多个相邻的原始聚类。此时必须先确认选取目标：

- 若把 Excel 每一行视为最终聚类单元，可直接使用该行的 `rep_trial + rep_step`；
- 若要求“每个原始 clustering 选一个负载”，应拆回 `C1`、`C2`，从未合并的 per-tool 聚类表分别选择，不能让合并行只产生一个负载。

当前生成逻辑下，合并行的代表样本可能来自合并前 `wall_s` 最大的子聚类，而不是对合并后全部成员重新计算得到的质心代表。因此，若合并行将被当作一个新的统计聚类，建议重新基于全部成员计算 cycles 加权质心和最近样本。

## 7. 输出要求

最终建议输出一份 `selected_workloads.xlsx` 或 CSV，至少包含：

| 字段 | 说明 |
|---|---|
| `workload_id` | 负载唯一编号 |
| `rank` | 在有效聚类中的排序 |
| `cluster_id` | 来源聚类 |
| `program` | 工具类型 |
| `n_steps` | 来源聚类规模 |
| `wall_s`、`cycles` | 来源聚类资源贡献 |
| 四个 Top-Down 指标 | 来源聚类特征中心 |
| `max_spread` | 聚类紧致度 |
| `rep_trial`、`rep_step` | 代表 step 定位信息 |
| `commands` | 完整命令序列，不使用截断预览代替 |
| `selection_rule` | 例如 `top_50pct_by_count/wall_s` |
| `validation_status` | `pending`、`passed` 或 `replaced` |
| `replacement_reason` | 若发生替换，填写具体原因 |
| `source_hash` | 输入文件版本标识 |

同时输出未入选聚类清单和异常清单，使结果可复核、可重现。

## 8. 验收标准

负载集满足以下条件时可交付：

1. 入选聚类数严格等于 `ceil(N/2)`；
2. 每个入选聚类恰好映射到一个代表负载；
3. 所有代表负载都能追溯到唯一的 `rep_trial + rep_step`；
4. 完整命令来自 step 明细，而不是来自截断的 `rep_cmd`；
5. 排序、并列处理、异常排除和代表替换均有记录；
6. 合并聚类的解释口径已经明确，并在结果中注明；
7. 试运行和代表性验证结果完整保存。

## 9. 方法边界

本方法代表的是选定指标空间中的 CPU 微架构特征，不自动保证语言、业务场景、命令意图、I/O 行为、内存占用或长尾时延同样具有代表性。若最终负载集还需要这些维度的覆盖，应在“前 50%”筛选之后增加分层覆盖或多指标约束，而不能只依赖 Top-Down 聚类结果。

## 10. 典型负载采纳前需要回答的问题

筛选方法只能回答“如何从已有样本中选出负载”。要使处理器产品团队接受这些负载作为 Agent 场景的典型负载，还需要建立如下完整证据链：

```text
真实 Agent 场景
  → 原始数据具有代表性
  → 聚类和抽样方法合理
  → 代表负载可稳定复现
  → 负载能够反映目标平台能力
  → 测试结果可解释、可维护
```

### 10.1 负载代表的 Agent 场景是什么

需要明确本负载集的定义和边界：

- 面向 Coding Agent、通用工具 Agent，还是其他类型的 Agent；
- 是否覆盖代码检索、文件读取、修改、编译、测试、依赖安装、版本控制和失败重试；
- 是否包含大模型推理、网络等待和 Agent 调度；
- 代表的是完整端到端 Agent，还是 Agent 驱动的容器侧工具执行负载；
- step、command、trial 和完整任务分别是什么，最终负载采用哪一种粒度；
- 是否保留失败命令，以及失败和重试为何属于真实 Agent 行为。

若当前数据不包含模型推理，建议将适用范围表述为：

> 本负载集代表 Coding Agent 在软件仓库中进行探索、修改、构建和验证时产生的本地计算侧负载，不代表大模型推理服务本身。

### 10.2 原始样本是否具有代表性

应提供聚类前的总体数据画像，而不只是最终选中的样本：

| 需要回答的问题 | 建议提供的证据 |
|---|---|
| 数据规模有多大 | trial、step、command 总数及采集时间范围 |
| 覆盖哪些语言 | 各语言的任务数、step 数和执行时间占比 |
| 覆盖哪些任务行为 | 检索、编辑、编译、测试、包管理等行为的分布 |
| 覆盖哪些项目规模 | 仓库大小、代码量和依赖规模分布 |
| 成功和失败如何分布 | 成功率、超时率和非零退出率 |
| 是否来自单一 Agent | Agent、模型、工具链和版本分布 |
| 是否存在采样偏差 | 数据来源、过滤规则、缺失数据及排除样本 |

同时需要解释这些数据代表的是一次特定实验，还是能够近似反映更广泛的 Agent 使用场景。

### 10.3 为什么选择前 50%

除本说明书第 2 节的默认口径外，还应提供以下证据：

- 前 50% 是按聚类数量、累计 `wall_s`，还是累计 `cycles` 定义；
- 为什么使用 `wall_s` 作为主要排序依据；
- 入选集合覆盖原始总体多少 `wall_s`、`cycles`、step 和 trial；
- 是否覆盖所有主要语言、program 和行为类型；
- 将比例调整为 40% 或 60% 后，核心负载集合是否稳定；
- 被排除部分是低频重复负载，还是包含了低频但重要的瓶颈。

最终报告不应只陈述“选择前 50%”，而应给出类似以下的量化结论：

> 入选的 X 个聚类覆盖原始数据 Y% 的执行时间、Z% 的 CPU cycles、N 种主要工具和全部目标语言；选择比例在 40%～60% 之间变化时，核心代表负载集合保持稳定。

### 10.4 每簇一个负载能否代表整簇

应报告聚类质量和代表点质量：

- 特征选择和聚类阈值的依据；
- 各聚类的成员数和 `max_spread` 分布；
- 簇内紧致程度和簇间差异；
- 代表点到 cycles 加权质心的距离；
- 更换随机种子或采集批次后的聚类稳定性；
- 代表负载重跑后是否仍处于原聚类范围内。

对于合并聚类，还应确认代表样本是合并后重新计算的质心最近样本，还是直接继承自某个子聚类。若是后者，必须说明其局限性或重新计算代表点。

### 10.5 是否覆盖 Agent 的关键负载形态

Top-Down 四象限主要反映 CPU 流水线特征，不能独立证明负载集覆盖了完整的 Agent 行为。建议补充分析：

- CPU 利用率、IPC、用户态与内核态比例；
- 指令数、分支及分支预测失败；
- L1/L2/LLC 缓存、TLB 和内存带宽；
- 磁盘和文件系统 I/O；
- 进程创建、系统调用和上下文切换；
- 单线程与多线程特征；
- 短命令启动型与长时间计算型负载；
- 编译、测试、解释执行、代码搜索等行为覆盖。

这部分用于证明入选的是“Agent 典型负载”，而不仅是“Top-Down 特征相似的 CPU 负载”。

### 10.6 选择方法是否具有跨平台有效性

若聚类数据来自与目标平台不同的处理器架构，需要回答：

- 源平台和目标平台的 PMU 事件定义是否一致或可比；
- 在源平台计算的 Top-Down 特征能否用于选择目标平台负载；
- 负载的聚类关系、排序和瓶颈分类在目标平台是否保持稳定；
- 是否将源平台的微架构特性误当成了负载自身的固有属性。

建议在目标平台重新采集代表负载，并抽取部分同簇非代表负载作为对照，验证代表点仍能描述其所在聚类。特征可分为：

- 相对架构无关特征：命令类型、执行时间结构、并发度、I/O 量和工作集等；
- 架构相关特征：Top-Down、缓存缺失、分支预测和其他 PMU 指标。

### 10.7 负载能够评价哪些产品能力

需要建立负载与处理器能力之间的对应关系，回答：

- 能否区分不同处理器型号或产品代际；
- 对核心数、频率、缓存、内存带宽和 NUMA 是否敏感；
- 能否反映编译器、运行时和操作系统优化效果；
- 是否存在大量过短命令，导致主要测量进程启动或容器开销；
- 单 Agent 串行与多 Agent 并发是否都需要覆盖；
- 能否用于产品对比、性能回归、容量规划、调优定位和场景演示。

建议形成如下映射：

| 负载类型 | 主要压力 | 可评价的能力 |
|---|---|---|
| 编译与构建 | 前端、分支、并行计算 | 核心性能、编译器和扩展性 |
| 测试执行 | 解释器、进程创建、文件访问 | 单核性能、操作系统和文件系统 |
| 代码检索 | 缓存、内存和文件读取 | 内存层次和 I/O |
| 多 Agent 并发 | CPU、内存和调度竞争 | 吞吐量、NUMA 和能效 |

### 10.8 如何评价处理器，而不只是描述负载

负载的选取指标与产品的评价指标应分开定义。评价指标可包括：

- 单任务完成时间；
- 单位时间完成的 Agent 任务数；
- P50/P95 时延；
- CPU 时间和峰值内存；
- 能耗和性能功耗比；
- 多 Agent 并发吞吐；
- 单任务成本；
- 正确性和任务成功率。

还应明确总分的聚合和权重。每个聚类选择一个负载，不代表所有负载应等权。可以按照原始出现频率、`wall_s` 或 `cycles` 分配权重，并同时报告分项结果，避免低频小聚类与高频大聚类对总分产生相同影响。

### 10.9 是否可以公平、稳定地复现

应形成统一运行规范，至少规定：

- 操作系统、内核、容器镜像和工具链版本；
- 编译器、解释器和依赖版本；
- CPU 绑核、NUMA、SMT、频率和功耗策略；
- 冷缓存或热缓存条件；
- 网络访问策略；
- 超时和失败处理规则；
- 重复次数、预热方法和置信区间；
- 后台噪声、温度和降频控制；
- 命令退出码、输出和文件副作用校验。

尤其需要证明重放没有改变原始行为。例如，超时和子进程清理策略不同，可能系统性放大或缩短负载。

### 10.10 负载能否交付并长期维护

正式采纳前还应确认：

- 是否可以离线运行；
- 是否依赖外部网络、私有仓库或凭据；
- 数据、代码和依赖的许可证是否允许分发；
- 是否包含敏感信息；
- 是否支持一键部署和执行；
- 单次运行的时间和资源预算；
- 如何进行版本化和变更记录；
- Agent 生态变化后多久更新一次；
- 新旧版本的测试结果是否可比。

### 10.11 建议配套的交付材料

除本说明书外，建议配套准备：

1. Agent 负载范围与原始数据说明；
2. 聚类质量与前 50% 覆盖率报告；
3. 代表负载重放一致性报告；
4. 目标平台交叉验证报告；
5. Benchmark 运行与环境规范；
6. 指标、权重与评分规则；
7. 负载清单及全链路追溯表；
8. 适用范围、局限性与版本维护策略。

其中应优先补强以下三项：

1. 前 50% 覆盖了总体多少真实执行量；
2. 代表关系在目标平台上是否仍然成立；
3. 这套负载能够评价处理器的哪些具体能力。
